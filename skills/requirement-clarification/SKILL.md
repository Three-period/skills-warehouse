# 需求调研与澄清 Skill

## 1. 定位与适用范围

目标：从零散诉求、访谈纪要、会议记录或业务描述中识别真实问题，明确目标、约束与信息缺口，为后续决策提供可靠依据。

适用：需求尚不清晰、资料不完整、不同业务方说法矛盾、需要业务调研提纲或需求澄清清单。

不适用：已确定业务规格且只需页面交互设计；要求直接开发代码；将需求方提出的功能方案不经分析直接转成事实。

Skill独立运行，不要求先使用任何其他Skill。

## 2. 输入识别

优先读取：需求原话、业务场景、提出方及使用者、现状流程、目标/指标、相关系统、样本文件、时间和资源约束。

按四类标记信息：
- **已确认事实**：明确来源或已有证据；
- **业务方诉求**：谁希望改变什么；
- **假设/推断**：尚未验证的原因、规则和影响；
- **待确认事项**：会影响范围或方案的关键缺口。

若只有一句模糊需求，也可先给出初步问题定义和高优先级澄清问题，不要虚构现状、指标或系统能力。

## 3. 执行步骤

### 步骤一：把“要什么功能”转为“为什么要改变”

依次识别：
1. 谁在什么场景下遇到什么问题？
2. 目前怎么解决，代价是什么？
3. 改变后期望达到什么业务结果？
4. 怎样知道问题得到改善？

如“想做AI自动审核”，先澄清审核对象、现行标准、责任主体、例外和质量风险，不直接承诺AI替代审核。

### 步骤二：拆解场景与对象

按“角色—触发—活动—输入—判断—输出—接收方”拆解主要场景。

跨部门业务至少问清：
- 参与方分别做什么；
- 使用什么系统和文件；
- 什么动作触发下一方；
- 哪些信息必须传递；
- 失败或退回由谁处理。

### 步骤三：识别目标、范围与约束

分开记录：
- 业务目标与成功标准；
- 本次范围与明确不做的内容；
- 上游、下游和依赖；
- 时间、资源、合规、数据、技术限制；
- 已知风险与待确认假设。

不自行编造改进百分比或项目时间表。

### 步骤四：提出有价值的澄清问题

问题按决策影响排序：
- **P0 阻断**：缺少后无法定义正确流程、角色、范围或验收；
- **P1 重要**：影响设计细节、效率或质量；
- **P2 补充**：不阻碍第一轮方案。

每个问题说明为什么要问、由谁回答、答案将影响什么设计决策。
避免问“请详细介绍业务”等宽泛问题。

### 步骤五：形成可填写的清单

若面向业务方填写，把抽象问题写成可理解的字段，并提供示例：
- 不写“输入输出”，写“该节点需要读取哪些文件？由谁提供？文件格式是什么？”
- 不写“协作机制”，写“提交后由哪个岗位接收？在哪个系统中操作？”

同时保留“待确认、责任人、确认结果”列，方便会议闭环。

### 步骤六：整理需求结论

输出：
- 已确认问题与目标；
- 核心用户/角色及典型场景；
- 初步范围、约束和风险；
- 未确认问题及优先级；
- 建议的下一轮验证方式。

## 4. 关键规则

- 需求方说“要某功能”，不等于这个功能是最优解。
- 现状、诉求、设计建议、已确认规则必须分开。
- 优先核实真实案例，不能仅凭一方观点确认所有角色的流程。
- 不将“未提供”直接判断为“业务不存在”。
- 询问数量尽量少，优先提问会改变方案的事项。
- 不因缺乏所有细节阻碍能够开展的现状整理。

## 5. 输出规范

默认输出四项：
1. **需求初判**：一句话问题定义、目标和当前证据。
2. **现状与场景摘要**：主要角色和场景。
3. **需求澄清清单**：字段如下。
4. **确认与下一步**：优先核实的资料、人员和动作。

| 优先级 | 待确认问题 | 提问原因/影响决策 | 建议回答角色 | 当前依据 | 确认结果 |
|---|---|---|---|---|---|

用户只要求“明天可交差的一张表”，优先直接输出一张便于业务方填写的表。

### 示例（虚构）

诉求：“希望采购申请自动审批。”
需要优先澄清：金额分级规则、审批责任、例外条件、申请与订单之间的关系；在答案确认前，不将“所有申请自动通过”写为需求。

## 6. 质量检查

- [ ] 问题定义不是简单复述功能诉求。
- [ ] 已识别目标用户、主要场景、现状及影响。
- [ ] 目标、范围和约束区分清楚。
- [ ] 关键角色与上下游未遗漏。
- [ ] 问题清单具体、可回答，说明影响决策。
- [ ] P0问题确实影响方案正确性。
- [ ] 已确认内容与假设、待确认内容分开。
- [ ] 输出可直接用于访谈或需求评审。

## 7. 异常处理

- **观点冲突**：列出各方说法、证据和待裁定问题，不擅自选边。
- **时间紧迫**：保留P0和P1问题，先产出可执行清单。
- **业务方缺少术语知识**：用岗位、动作、文件和系统名称解释问题。
- **没有指标基线**：列出建议采集的基线数据，不填虚假数值。
- **用户要求继续产品设计**：说明已有信息是否足够；当前仅形成可交接的需求定义，不擅自编造详细PRD。
