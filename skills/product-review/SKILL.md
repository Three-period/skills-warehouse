# 产品方案评审 Skill

## 1. 定位与适用范围

目标：提供独立、可解释、可执行的产品质量评审。不是为了寻找问题而寻找问题；正确的设计应明确认可。

适用：业务流程、规格书、PRD、信息架构、核心交互、AI工作流、原型和验收方案评审。

不适用：要求凭空评审不存在的方案；只有UI视觉偏好但不涉及功能质量；默认直接替用户改代码或推送GitHub。

不依赖其他Skill。可直接评审用户粘贴、上传或提供可访问位置的材料。

## 2. 输入识别

尽可能获取：
- 待评审的方案或原型；
- 业务目标、目标用户、范围和阶段；
- 当前已确认业务规则；
- 上下游流程和技术约束；
- 已知风险、争议和验收要求。

若缺少业务依据，只能判断文档内部一致性及通用逻辑风险；不得假定真实业务规则一定如此。

评审时区分：
- **已证实问题**：可从提供材料直接定位的缺陷；
- **高风险假设**：合理但需验证的风险；
- **改进建议**：可选方案，不等同于必须修复的问题。

## 3. 执行步骤

### 步骤一：确定评审边界与完成标准

确认是全量评审还是某个模块。先复述目标、范围与限制，避免用通用最佳实践推翻已确认约束。

### 步骤二：从业务目标检查合理性

- 产品是否解决目标问题；
- 是否有业务场景未承载；
- 是否混入与目标无关的功能；
- 是否有更简单的达成路径。

### 步骤三：走查端到端主线

用至少一个具体场景，从触发走到结束：
- 谁发起；
- 输入从哪里来；
- 触发了哪个系统动作；
- 经过哪些判断；
- 哪些状态发生变化；
- 谁接收结果；
- 何时可以准出。

若无法走到终点，标记阻断位置和触发条件。

### 步骤四：走查关键异常

至少按适用范围检查：
- 资料缺失、重复提交、超时、工具失败；
- 驳回、异议、重新提交与回退；
- 多轮修改、版本不一致、旧结论失效；
- 未获授权操作或角色缺失；
- AI误报、漏报、无法判断和未执行范围。

不要机械假设每个产品都必须存在所有异常；只标记与当前业务相关的问题。

### 步骤五：检查跨层一致性

逐项比对：
业务规则 ↔ 流程 ↔ 角色/权限 ↔ 业务对象/状态 ↔ 页面操作 ↔ 下游结果 ↔ 验收用例。

具体检查：
- 同一名词是否指同一对象；
- 一处规则修改是否漏改其他图表；
- 按钮动作是否有状态/数据结果；
- 任务状态和问题状态是否混淆；
- AI与人工的责任界面是否清楚。

### 步骤六：评估落地与验收

- 实现依赖是否明确；
- 哪些能力已存在、哪些待开发；
- 是否有可执行的测试场景；
- 成功标准有无指标口径与证据；
- 是否把技术可行性或收益假设写成既成事实。

### 步骤七：给出优先级和修改建议

按影响分级：
- **P0 阻断**：核心流程无法完成、权限越界、数据错误导致结果无效；
- **P1 严重**：高频场景缺失、关键异常无法闭环、结果不可追溯；
- **P2 优化**：表达、易用性或后续维护改进，不影响核心可用性。

每条问题写明依据、触发场景、影响、建议修改和验收方式。没有证据的内容标记为风险假设。

## 4. 评审硬约束

- 不以增加模块数量衡量产品专业度。
- 不能编造业务事实、技术可行性或测试结果。
- 不把个人偏好包装成必须整改的问题。
- 不重新讨论已经明确且无新证据的设计决策。
- 发现问题要提供可复现路径与修正建议。
- 对当前方案合理的部分直接认可，不刻意制造分歧。
- 默认**只评审不修改**；收到明确修改指令后再执行。
- 优先最小化整改范围，避免因为一个问题推翻整套方案。

## 5. 输出规范

默认输出：
1. **总体结论**：通过 / 有条件通过 / 暂不通过，并说明判断依据。
2. **关键问题清单**：按P0→P1→P2排序。
3. **待验证假设**：与已确定缺陷分开。
4. **建议修改顺序**：前置依赖和最小闭环。
5. **复验场景**：改完后怎样确认问题已解决。

问题表：

| 等级 | 定位 | 问题/触发场景 | 影响 | 依据 | 修正建议 | 复验方式 |
|---|---|---|---|---|---|---|

如果用户只让检查一个局部交互，只输出局部发现和修正路径，不提供无关的大型审计报告。

### 示例（示意）

方案规定：“审批通过后可下单”，但未定义已修改申请是否需重新审批。
- 类型：高风险假设，而非已证实缺陷；
- 影响：可能存在旧审批结论被新版本沿用；
- 建议：明确修改内容是否使旧审批失效，形成版本校验规则；
- 验证：审批通过→修改关键申请内容→尝试下单，检查是否符合已确认业务规则。

## 6. 质量检查

- [ ] 结论有方案依据和明确范围。
- [ ] 缺陷与待验证风险分开。
- [ ] 发现的问题有可理解的触发条件。
- [ ] P0/P1/P2和实际影响一致。
- [ ] 修正建议可执行、不过度扩大范围。
- [ ] 核心业务闭环、角色、数据、状态已检查。
- [ ] 关键异常与下游结果已走查。
- [ ] 复验标准可操作。
- [ ] 合理设计也被客观认可。

## 7. 异常处理

- **资料不足**：说明只能评审哪些部分，列关键待验证事实，不虚构结论。
- **同一问题有多个解法**：比较成本、风险及适用条件，给出推荐方案但保留决策权。
- **业务与技术说法冲突**：说明决策归属与验证责任，形成待确认项。
- **时间紧急**：先聚焦阻断性问题、最小修复和关键回归场景。
- **用户明确要求代为修订**：先保留原始约束，再按确认范围修改并说明差异。
