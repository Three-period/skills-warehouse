# 产品方案与 PRD 设计 Skill

## 1. 定位与适用范围

目标：回答“产品用哪些功能和页面承载业务，用户如何操作，系统如何反馈和流转”，形成能支持原型、开发和测试的产品说明。

适用：功能规划、信息架构、角色化工作台、核心页面与交互、已有原型增量设计、AI功能的产品化承载。

不适用：尚未识别业务问题却要求虚构全部业务规则；仅需代码实现；仅需业务流程而不涉及产品承载。

独立运行，允许直接接受原始访谈或用户说明，不要求先调用需求或业务规格Skill。

## 2. 输入识别

优先识别：
- 产品目标、用户角色、核心业务场景；
- 现有业务规则、准入准出和状态；
- 输入输出文档、系统与数据来源；
- 现有页面或原型结构、导航、设计约束；
- 技术实现约束、首期范围和验收目标。

没有正式规格书时，可从用户提供的描述抽取临时业务依据，并显式列为“待业务确认”；不能擅自将假设固化到页面功能。

## 3. 执行步骤

### 步骤一：建立“业务活动→产品能力”映射

| 角色 | 业务目标/活动 | 产品支持能力 | 输入 | 操作结果 | 权限/限制 |
|---|---|---|---|---|---|

检查是否存在无法承载的业务活动、无明确价值的功能，以及同一职责被重复设计在不同模块的情况。

### 步骤二：确定产品范围与角色视图

- 标明此次新建、修改、复用和不涉及的功能。
- 根据角色任务与信息需求决定共用页面还是分角色视图。
- 保留现有平台已确认的导航与设计样式；增量修改默认最小变更。
- 不凭个人偏好新增管理员、主管或专家角色。

### 步骤三：设计功能架构与信息架构

功能架构回答“有哪些能力”，信息架构回答“在哪些页面或入口”。

区分：
- 一级/二级功能；
- 页面、抽屉、弹窗、标签页；
- 任务入口与详情；
- 配置管理与执行工作台。

每个页面应有明确角色与任务目的，避免为每个业务步骤都创建独立页面。

### 步骤四：设计关键页面与交互

逐页说明：
1. 页面定位、入口和使用角色；
2. 页面布局、主要信息区、组件与默认展示；
3. 操作入口、触发条件、表单与校验；
4. 成功反馈、失败提示、加载及空状态；
5. 操作后变化的业务对象、任务状态和下游动作；
6. 历史、版本和审计信息的查看方式。

将“看到一个按钮”与“业务动作真实完成”严格区分。

### 步骤五：设计跨角色联动

例如一方提交异议：
- 产生什么任务或记录；
- 另一方从哪里进入；
- 谁做决定；
- 结果返回哪里；
- 原始问题如何关闭或重新进入处理。

对于跨工作台操作，始终检查共享数据、状态一致性、版本校验和权限。

### 步骤六：设计AI能力的页面承载（适用时）

明确：
- AI输入来源与提交门槛；
- 运行中、完成、失败、未覆盖状态；
- 输出结果、依据、证据与不可判定项；
- 用户如何确认、反馈、纠错或转人工；
- 结果是否关联任务、版本与批次；
- 不可展示或不可实现的能力应明确为待评估。

### 步骤七：制定验收用例

每项核心功能写清：
- Given：角色、资料、业务状态和版本；
- When：用户执行什么操作；
- Then：展示、数据、状态、消息与下一步应是什么。

覆盖正常、异常、权限和版本变化场景。

## 4. 关键规则

- 业务逻辑先于页面交互，不能通过按钮设计反向创造未经确认的审批规则。
- 功能架构与信息架构是不同层次，不混作一张图。
- 页面设计服务于角色任务，不为了“完整”堆叠无关模块。
- 已有原型默认局部增量修改，保留其他已确认页面。
- 权限、状态和数据联动必须与业务角色一致。
- AI输出需要显示证据、适用范围和未判定项，不用“AI已通过”掩盖未执行范围。
- 对尚未验证的技术能力标注待评估，不承诺虚假功能。

## 5. 输出规范

根据任务规模选择，不必每次输出全套。

完整PRD建议包含：
1. 背景、目标、范围及现状约束；
2. 用户、角色与主要使用场景；
3. 业务活动与功能映射；
4. 功能架构图；
5. 信息架构图；
6. 页面清单、布局和交互规则；
7. 权限矩阵与关键状态；
8. 数据来源、关联和版本交互；
9. 异常处理、消息和回流；
10. 验收用例、待确认事项。

页面设计细节使用表格和文字，架构图可使用Mermaid。只有在用户要求HTML原型或可运行代码时，才进一步按工具能力生成。

### 示例（示意）

“采购申请待审批页面”：
- 列表展示申请编号、申请人、金额、状态；
- 审批角色打开详情，查看附件和审核记录；
- 通过/退回按钮按当前权限与业务状态启用；
- 退回必须记录原因；决定写入审核历史并通知申请人；
- 审批阈值规则待业务方提供，不自行设定。

## 6. 质量检查

- [ ] 每个核心功能对应业务活动或明确价值。
- [ ] 功能架构与页面入口一致。
- [ ] 角色权限正确，无越权操作。
- [ ] 页面展示、提交和状态变化前后一致。
- [ ] 正常、空、加载、失败和异常状态有处理。
- [ ] 多版本资料和历史记录可追溯。
- [ ] 跨工作台交接有入口、责任人和反馈去向。
- [ ] 实现边界、依赖和待确认内容明确。
- [ ] 验收用例可执行，不停留在“页面展示正确”。

## 7. 异常处理

- **业务规则缺失**：交付可确定的页面骨架，把受影响交互标记待确认。
- **已有原型结构冲突**：指出冲突和最小变更方案，不整体重构。
- **多个角色需求冲突**：根据职责和使用任务对比统一视图与分角色视图。
- **系统接口不可用**：区分真实能力、Mock演示和待开发接口。
- **用户只需要页面方案**：只交付信息架构、页面与交互，不扩写整份PRD。
