# B 端业务逻辑设计 Skill

## 1. 定位与适用范围

**目标**：回答“某个业务动作为什么允许、改变什么状态、如何影响上下游，以及哪些情况必须阻断”，使原型具备可验证的业务行为。

适用：
- 为 B 端原型构建审批、流转、退回、重试、移交和完结规则；
- 定义角色权限、业务对象状态、状态转换和前置门禁；
- 设计跨页面、跨角色、跨阶段的数据关联和版本一致性；
- 为 Mock 原型制定可重复的正常、异常及多版本演示场景；
- 排查“按钮显示成功但下一阶段未解锁”等状态不一致。

不适用：
- 只有宏观访谈内容，尚未要求可执行的节点级业务规则；
- 单纯视觉交互、数据库物理表、接口协议或框架实现；
- 根据通用经验代业务方决定真实审批人、时限和组织规则。

独立运行，不要求读取其他 Skill。业务事实与为原型提出的设计假设必须分开。

## 2. 输入识别

接受业务描述、SOP、PRD、流程图、审批规则、现有原型、代码状态定义、测试记录等。

优先识别：
1. **业务对象**：项目、单据、任务、报告、问题、审批记录、提交版本等；
2. **参与者**：提交、执行、审核、接收、撤回的角色与责任；
3. **触发事件**：何时提交、通过、退回、重试或失效；
4. **状态与门禁**：当前状态、目标状态和准入准出条件；
5. **数据基准**：项目、版本、批次、Commit、文档等关联标识；
6. **例外与历史**：重复提交、版本更新、审批作废、回滚、跨项目隔离；
7. **演示边界**：真实系统反馈还是 Mock 模拟，是否持久化。

关键规则未确认时明确列出待确认项，不把推断写成公司现有制度。

## 3. 执行步骤

### 步骤一：选定业务闭环和边界

先写出本次闭环：起点事件 → 业务判断 → 状态结果 → 结果接收方。

明确本次是单节点逻辑、跨节点联动，还是完整端到端业务链。避免把“阶段”“业务对象”“页面标签”混作同一个状态。

### 步骤二：定义对象和状态

逐个业务对象定义允许的状态、含义、创建与更新责任：

| 业务对象 | 状态集合 | 状态所有者 | 产生事件 | 下游使用者 |
|---|---|---|---|---|

例如报告可以处于“草稿/待评审/审核通过/已退回”，阶段可以处于“未启动/进行中/已准出”；**报告通过不必然等于阶段准出**，除非业务规则明确如此。

区分派生状态与人工录入状态。能根据审批记录与版本一致性计算出的状态，不应在多个页面维护互相矛盾的独立副本。

### 步骤三：构建状态转换表

每条转换明确：
- 当前状态；
- 事件及发起角色；
- 守卫条件（权限、前置完成、资料、版本）；
- 成功后的状态与业务记录；
- 失败时阻断原因及返回路径；
- 是否影响下游任务或阶段。

| 对象/当前状态 | 触发事件 | 角色 | 守卫条件 | 新状态/副作用 | 失败或回退 |
|---|---|---|---|---|---|

注意“点击按钮”只是事件，**审核结果被有效确认并写入记录**才可能成为准出依据。异议裁定、报告审核、最终阶段审批等不同动作必须单独建模。

### 步骤四：设计角色权限与职责边界

为重要动作建立角色 × 状态 × 动作矩阵。明确谁能查看、编辑、提交、审核、撤销、执行例外操作。自动规则可以控制门禁，但业务审批的责任和记录不能无依据地归给 AI 或系统。

权限不足、阶段未开放和资料不齐要区分原因，不通过隐藏按钮代替真实权限规则。

### 步骤五：确定跨模块数据锚点

为每条业务链确定唯一可信来源：
- 哪个对象是版本/批次/项目的主记录；
- 哪个事件生成正式移交凭证；
- 下游从哪里读取有效状态和版本；
- 相同动作的多个入口是否写入同一份记录；
- 历史结果何时保留、何时失效、何时禁止继承。

建议采用“主业务对象 + 关联标识 + 独立审批记录 + 派生门禁”的模型。多个页面不能分别保存独立的“已通过”布尔值并假定自动一致。

### 步骤六：定义异常与重入

覆盖当前场景实际相关的：
- 前置资料缺失或审批被退回；
- 同一动作重复执行、并发或误点；
- 新版本出现，旧审批/报告是否仍有效；
- 操作进行中失败、未完成、重试或撤回；
- 角色切换、项目切换、跨工作台回流；
- Mock 初始化、切换场景、重置后是否留下陈旧状态。

**禁止通过无条件放开下一阶段来掩盖状态读写错误。**

### 步骤七：用场景验证状态机

至少设计一条正常流程、一条前置阻断、一条退回重试；涉及版本时增加“旧版通过 → 新版提交 → 旧结论失效”及“跨项目隔离”。

采用 Given / When / Then：
- Given：角色、对象、当前状态、关联版本；
- When：执行业务事件；
- Then：更新哪条记录、显示何状态、哪个动作开放或被阻断。

## 4. 关键规则

- **对象与阶段分别建模**：单据通过、报告通过与阶段准出不能默认等同。
- **单一可信状态来源**：不同页面和入口调用相同业务判断，避免重复维护冲突状态。
- **守卫条件必须可解释**：既不能让合法流程无故阻断，也不能跳过审批直接解锁。
- **动作与记录成对存在**：通过、退回、发布、结项都要有可追溯的结果及责任信息。
- **版本一致才可继承结论**：关联对象变化后明确旧审批的有效性，不让旧版结论冒充新版。
- **失败不污染下游**：未通过的动作不能写出已发布、已结项等成功状态。
- **Mock 模拟必须真实于规则**：可以使用模拟数据，不可以用假的成功提示代替状态转换。
- **不发明真实制度**：角色、阈值、时间与特批规则若无依据，一律待确认。

## 5. 输出规范

按任务规模选择，默认包括：
1. **业务对象与目标闭环**：列出边界和已确认规则；
2. **状态模型**：对象、状态集合、有效性来源；
3. **转换与门禁表**：事件、角色、前置条件、结果、阻断；
4. **跨模块数据关系**：关联标识、读写主体、版本一致性；
5. **场景验收**：正常、异常、重新提交、版本变化；
6. **待确认决策**：缺失规则及其影响。

示例（模拟研发场景，并非通用强制制度）：

| 事件 | 前置条件 | 状态/数据结果 |
|---|---|---|
| 人工检视准出 | 当前 Commit 已完成规定检视 | 创建当前版本移交记录 |
| 测试阶段审批通过 | 审批记录关联正式移交 Commit | 测试阶段准出，发布可操作 |
| 报告单独审核通过 | 报告记录满足审核条件 | 仅更新该报告，不自动代表测试阶段准出 |
| 新 Commit 提交 | 与已移交 Commit 不同 | 依已确认规则重新判定旧审批与下游结果有效性 |

如果只要求修复一个失效门禁，直接给出状态读取点、写入点、缺失关联、最小修正规则和复验用例，不扩展为完整业务规格书。

## 6. 质量检查

- [ ] 各业务对象及其状态有清晰定义。
- [ ] 状态转换由明确事件触发，有责任角色和守卫条件。
- [ ] 正常流程有终态，退回和异常有回到合法状态的路径。
- [ ] 角色权限与动作一致，没有未经授权的放行。
- [ ] 同一业务结论具有唯一可信来源，多个入口结果一致。
- [ ] 跨模块关联项目、批次、版本等必要标识。
- [ ] 新版本、重试和重复提交不会错误复用旧结论。
- [ ] 报告/过程交付物状态没有与阶段准出混淆。
- [ ] Mock 场景切换与重置不会串项目或串版本。
- [ ] 验收场景能证明既“该放行的能放行”，也“该阻断的能阻断”。

## 7. 异常处理

- **前后业务规则冲突**：列出不同依据及影响范围，不擅自选用其中之一。
- **只有 UI 描述无规则**：先建立最小状态假设并注明待确认，禁止假装已获业务认可。
- **旧代码有多套状态**：先定位实际读写链，不直接追加第三份状态；建议收敛可信来源。
- **用户报告“已通过却未解锁”**：追踪按钮事件 → 写入对象 → 门禁读取 → 版本校验 → 页面状态，而不是只修改提示文案。
- **缺少真实接口**：提供可重复的 Mock 状态设计，明确真实接口及并发保证待技术评估。
- **只请求逻辑设计**：不默认修改代码、提交 GitHub 或接管完整项目管理。
