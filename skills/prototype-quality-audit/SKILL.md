# 原型质量审计 Skill

## 1. 定位与适用范围

**目标**：判断“需求是否真正体现在当前原型里、用户能否走通、是否破坏旧功能”，并给出可定位、可复验、有证据的结论。

适用：
- 已有 HTML、Web、低代码或其他可交互原型的功能核查；
- 一次修改完成后的自检与上下游回归；
- 连续多轮修改（通常约三轮）后的累计需求追溯；
- 流程、角色权限、状态、跨模块数据相关的专项审计；
- 缺陷修复后确认原问题已解决、且没有引入新问题。

不适用：
- 仅有业务构想、没有原型时声称“功能测试通过”；
- 仅需审查 PRD 文档合理性而非已实现功能；
- 未获授权时直接重写原型或提交代码。

此 Skill 独立运行，不依赖聊天记忆或其他 Skill。可以利用提供的需求、源码、截图、演示路径、测试记录和已有交付证据。

## 2. 输入识别

尽可能获得：
1. **待审计版本**：当前原型链接/文件/分支与版本标识；
2. **需求基准**：本轮和历史已确认的修改要求、验收条件、不变范围；
3. **业务路径**：角色、入口、前置操作、正常及异常场景；
4. **实现与运行材料**：源码、运行环境、Mock 数据、日志、截图；
5. **历史风险**：重复缺陷、跨阶段修改、此前未通过的用例；
6. **工具边界**：是否能访问源码、浏览器、测试环境和 Git 仓库。

用户没有完整历史需求时，只能审计已提供的需求与当前实现，并说明历史覆盖范围不足；不补造不存在的需求编号或测试结果。

## 3. 执行步骤

### 步骤一：确定审计基准与范围

先确认实际被检查的是哪个版本。不得仅凭文件名、页面标题或聊天中声称的版本认定源码已同步。

选择检查深度：
- **局部检查**：单个需求、控件或页面；
- **增量检查**：本轮修改与直接上下游；
- **累计审计**：最近若干轮需求的覆盖与冲突；
- **里程碑审计**：核心端到端路径及高风险异常。

变更涉及角色、流程门禁、状态机、版本关联时，即使只改一处，也扩大相关业务链路的回归范围。

### 步骤二：建立轻量需求追踪矩阵

逐条把“已确认要求”映射到“实际实现位置”和“可观察结果”。

| 需求/规则 | 原定验收条件 | 实现位置/入口 | 实际验证方法 | 证据 | 结论 |
|---|---|---|---|---|---|

不要将“找到代码”“按钮存在”“页面截图正确”直接等同于交互及业务通过。

### 步骤三：分层验证

按证据能力分层执行：

**L1 静态检查**
- 文件完整、版本可识别、无明显语法或结构错误；
- 需求字段、文案、入口和关键逻辑是否存在；
- 数据读写是否引用正确对象，是否遗留重复旧监听与旧状态分支。

**L2 交互检查**
- 页面入口、导航、抽屉、弹窗、按钮、输入、保存、关闭和返回；
- 空数据、加载、报错、禁用和反馈；
- 无权角色是否能操作，未启动阶段是否只是可查看。

**L3 业务闭环检查**
- 选取代表性真实业务场景，按操作顺序执行；
- 追踪事件触发、状态写入、下游读取、门禁、最终结果；
- 核对同一对象在不同页面/工作台的状态和关联版本；
- 确认失败动作不会出现假成功或不合理的阶段放行。

**L4 回归与交付检查**
- 测试本次修改的上下游、高风险旧路径及跨角色操作；
- 核对新旧需求有没有互相覆盖或冲突；
- 若涉及 Git 提交，核对目标分支、文件、Commit 与远端内容。

能使用真实浏览器与测试工具时尽量实测；不能使用时明确“仅静态检查”，不可生成虚假的截图、操作记录或测试通过结论。

### 步骤四：设计代表性用例

至少根据实际风险覆盖：
- 正常：满足前置条件，能到达正确结果；
- 阻断：资料不足、未获授权或状态不满足时拒绝执行；
- 退回：驳回、重新提交、修复后重试；
- 版本：旧版已通过后切换到新版，核对审批是否被错误继承；
- 跨页面：不同工作台或入口读取同一结果；
- 项目隔离：A 项目的状态不能错误进入 B 项目。

测试用例使用 Given / When / Then 或“前置—操作—期望—实际”表达；不适用的场景不强行凑数。

### 步骤五：分类结论与证据等级

为每条需求使用互斥结论：
- **已验证完成**：完成实现，且在说明的范围内有可复验的验证证据；
- **已实现未验证**：有实现依据，但缺少必要运行或交互验证；
- **部分完成**：只满足一部分验收条件；
- **未完成**：需求未实现或无法达到关键结果；
- **存在缺陷**：实现可见，但已观察到与验收标准冲突的行为。

若材料不足以判断，单独记为“无法判断 / 待补充证据”，不能强行定为未完成或通过。

区分三类发现：
- **已复现缺陷**：有触发步骤和实际结果；
- **高风险推断**：可能导致故障，但未复现；
- **优化建议**：不影响核心验收的可选改进。

### 步骤六：按影响分级并给出修复/复验路径

- **P0 阻断**：核心端到端流程断裂、严重越权或关键数据结果错误；
- **P1 严重**：重要场景不可用、数据不一致、异常无法闭环；
- **P2 一般**：次要交互问题、文案歧义、非阻断性体验缺陷。

每个问题写清：定位、前置、复现步骤、期望、实际、证据、可能根因（注明是否已证实）、最小修复建议、复验方式。不要把推测根因描述成确认事实。

### 步骤七：形成审计结论并沉淀典型问题

汇总已验证/未验证范围、阻断项、残余风险和推荐下一步。对重复出现的关键缺陷，沉淀可迁移规则：

**场景 → 表现 → 根因依据 → 修复原则 → 验收场景 → 防再发检查点。**

不为一次性小修强制输出大型总结；累计审计关注本轮及历史需求是否被遗漏。

## 4. 关键规则

- **源码存在不等于功能可用**，语法通过不等于交互通过，交互通过不等于业务闭环通过。
- **提交成功不等于验收完成**；明确已提交与已实际验证的区别。
- **证据驱动结论**：没有浏览器环境就不得宣称已逐按钮验证。
- **需求是验收基准**：不得把未经确认的改进建议当成历史必做需求。
- **历史版本不覆盖最新版本**：源文件来源不明时暂停危险写入。
- **正常与异常都要检查**：既确认合法场景能放行，也确认非法场景被阻断。
- **最小范围修复**：默认只提供审计结论和改法，未经明确授权不直接修改代码。
- **自检不能只靠自述**：必须指出具体验证动作、结果、证据或验证能力边界。

## 5. 输出规范

默认先给一句审计结论，再给紧凑矩阵和 P0/P1/P2 问题清单。

推荐主表：

| 需求/用例 | 验收标准 | 实际结果 | 验证方式/证据 | 状态 | 优先级 |
|---|---|---|---|---|---|

交付包括：
1. 版本、审计范围和输入证据；
2. 逐项需求追踪与验证状态；
3. 关键缺陷及复现路径；
4. 未覆盖、待确认和环境限制；
5. 建议修复顺序与复验用例。

示例（示意，非实际测试结论）：

- **需求**：检视通过后开放测试阶段；
- **预期**：当前 Commit 通过人工检视，测试入口可操作；
- **实际**：页面显示“通过”，但下游入口禁用；
- **发现**：两处页面读取不同审批状态（需以真实代码/操作证据核实）；
- **建议**：统一状态写入和门禁读取，复验新旧 Commit 及合法/非法角色。

如果用户只要求“检查某按钮能不能工作”，仅返回该问题的复现、判断和修复建议，不强制输出整套报告。

## 6. 质量检查

- [ ] 已核对实际审计版本和范围。
- [ ] 需求依据明确，没有凭记忆杜撰历史条件。
- [ ] 每项结论对应明确验收条件和证据类型。
- [ ] 静态、交互、业务、回归四层验证没有混为一谈。
- [ ] 核心路径具有可复验的前置、操作、期望、实际。
- [ ] 角色越权、前置阻断、失败重试和版本关联得到适用检查。
- [ ] 多轮需求被逐项追踪，没有仅核查最新一轮。
- [ ] 已复现问题、风险推断和优化建议清晰分开。
- [ ] 修正建议不会绕过业务门禁或扩大无关修改。
- [ ] Git 交付状态和未验证事项真实透明。

## 7. 异常处理

- **源码或最新版本不可访问**：说明无法核验版本，不用猜测版本作肯定结论；不直接覆盖仓库。
- **只能读取代码、无法运行浏览器**：输出静态检查结果，交互与端到端验证标为未验证。
- **缺少历史需求**：只对可得需求审计，列出覆盖缺口；不假装全量追溯已完成。
- **多个版本结果冲突**：先比对分支、文件和提交记录，避免把缓存页面当最新版本。
- **发现 P0 阻断**：优先给出可复现路径与最小安全修复建议；默认不自动修改。
- **修复后仍失败**：复查事件监听、状态写入、下游门禁、Mock 初始化和版本锚点，不把“已有补丁”当成问题解决。
- **用户明确授权修复**：在实际工具可用的范围内修改，随后重新审计并报告验证限制；本 Skill 不承担独立 Agent 调度。
