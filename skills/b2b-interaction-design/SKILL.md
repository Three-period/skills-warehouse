# B 端交互设计 Skill

## 1. 定位与适用范围

**目标**：把角色的真实任务转化为清晰、一致、可操作、可验收的 B 端页面交互，而不只是画出可点击的界面。

适用：
- 设计后台、工作台、项目管理、任务处理、配置台、知识库等 B 端 Web 页面；
- 判断导航层级、信息分组、组件选型、操作位置和反馈方式；
- 修改已有原型的交互，消除重复入口、冗余字段、页面操作歧义；
- 检查同类功能在不同页面、角色视图中的一致性。

不适用：
- 业务规则尚未确认时，代业务方决定审批权或准入条件；
- 仅要求完整业务流程建模、技术架构、数据库结构或前端编码；
- 仅凭个人偏好主张特定视觉风格。

本 Skill 独立运行，不要求调用其他 Skill。业务规则未知时，只设计不依赖未知规则的界面部分，并标记待确认。

## 2. 输入识别

从用户描述、截图、原型、现有页面、PRD 或业务场景中提取：
1. **任务与角色**：谁在什么场景下，要完成什么，频率和风险如何；
2. **入口与层级**：在哪个工作区进入，列表、详情和任务入口如何关联；
3. **业务对象**：操作的是项目、单据、问题、审批记录还是版本；
4. **已有约束**：现有导航、组件、术语、页面布局及明确不改的范围；
5. **可操作条件**：角色权限、对象状态、前置条件及操作后的结果；
6. **数据与反馈**：默认值、空状态、加载、失败、历史、审计和 Mock 边界。

仅在信息缺失会影响关键交互时精准提问；其他缺口标记“待确认”，不自行编造组织角色或业务事实。

## 3. 执行步骤

### 步骤一：建立角色—任务—页面映射

先回答：谁进入这里、最重要的任务是什么、从哪里来、做完去哪里。

| 角色 | 核心任务 | 入口 | 关键数据 | 主要操作 | 操作结果/去向 |
|---|---|---|---|---|---|

同一角色的高频任务应易于到达；低频配置与高频执行任务不应混排。不同角色是否共享页面，要根据任务、信息需求和权限判断，而非一律复制工作台。

### 步骤二：组织信息架构与页面层级

- 区分导航（模块位置）、标签（同一对象的视角）、步骤（有顺序的任务）与筛选（同页数据范围）。
- 核对一级、二级导航与页内导航是否重复表达同一层级。
- 区分**对象详情**与**操作表单**，不要因一个审批动作复制整套页面。
- 页面应优先呈现当前任务所需的信息；相关依据、历史和扩展信息可渐进展开。
- 对已有原型优先保持入口与信息架构稳定，必要的调整明确变更范围。

### 步骤三：依据任务选择交互组件

| 场景 | 优先方案 | 判断理由与注意事项 |
|---|---|---|
| 多记录检索、对比、批量操作 | 表格 + 搜索/筛选 | 关键列可扫描；避免每列同时堆积按钮 |
| 项目总览、指标与状态 | 概览卡片 + 明细入口 | 指标口径明确；卡片不是替代全部明细 |
| 查看单个对象或短表单 | 抽屉 | 保持列表上下文；长流程不宜硬塞抽屉 |
| 高风险确认、简短决策 | 弹窗 | 说明后果；禁止把复杂表单塞进确认弹窗 |
| 多环节、长文本工作 | 独立页面或工作区 | 提供导航、保存和返回机制 |
| 当前节点的轻量辅助信息 | Tooltip / Popover | 仅展示摘要，不隐藏必须读取的关键操作信息 |

组件选型应服从任务复杂度、上下文保留、使用频率和风险，不机械套用。

### 步骤四：定义操作与反馈

每个关键交互至少明确：
- **前置条件**：什么角色、什么对象状态、什么资料条件下可操作；
- **触发方式**：点击、悬停、输入、提交、快捷键等；
- **动作结果**：生成或改变什么数据、记录、任务或状态；
- **页面反馈**：成功、失败、处理中、禁用、空、无权限时分别显示什么；
- **返回路径**：提交、保存、关闭后用户去哪里；
- **重复操作**：重复提交、撤回、刷新、切换视图时如何表现。

区分“不可见”“可见但只读”“可操作”。被禁用的按钮应尽可能解释原因，不能仅通过灰色代替说明。

### 步骤五：统一表单、审批与跨角色交互

- 区分保存草稿、提交评审、审核通过、退回和正式发布，不用一个按钮模糊多个业务动作。
- 必填项由真实业务规则决定；自动回显已有字段，避免同一资料重复录入。
- 退回、驳回及高风险操作需要明确反馈和必要的原因记录；是否强制填写原因以业务规则为准。
- 一方提交后，明确另一方在哪里看到待办、怎样处理、结果如何返回原页面。
- 不把正文评论、测试报告审核等过程动作误设计成阶段准出操作。
- 交互文案尽量采用“动作 + 对象”，避免多个不同结果都叫“审核通过”。

### 步骤六：设计可见的状态与追溯

为适用页面定义：初始、加载、空数据、部分数据、成功、失败、无权限、已失效/版本不一致等状态。

涉及多版本、多角色协同时，显示必要的责任人、关联版本、处理时间、当前状态和历史入口。Mock 演示须标注为 Mock，不能暗示真实服务已经运行。

### 步骤七：场景走查与最小修改建议

按用户任务走一条正常路径和至少一条关键异常路径；检查不同入口是否指向同一业务对象、同类操作文案和反馈是否一致。已有原型只提出必要的增量改动，保留用户明确要求不变的部分。

## 4. 关键规则

- **任务优先于装饰**：布局与组件必须服务于业务任务，不为丰富页面增加重复卡片和字段。
- **交互不能创造业务规则**：页面可以反映审批条件，不能擅自发明审批条件。
- **可见不等于可操作**：列表浏览、详情查看和执行动作的权限可以不同。
- **动作不等于状态结果**：按钮点击、报告提交与最终审批是不同事件。
- **同义操作一致**：同类组件、状态、按钮文案与反馈应保持一致。
- **重要状态不只靠颜色**：状态同时配文字或图形，避免仅用绿灯/红灯表达。
- **最小变更**：优化已有原型时不未经授权重做导航、权限或业务流程。
- **建议与事实分离**：通用模式是参考，不能取代用户已确认的实际业务约束。

## 5. 输出规范

根据任务颗粒度选择，默认给出：
1. 交互目标与适用角色；
2. 页面结构/入口与核心区域；
3. 交互规格表（入口、动作、前置条件、状态结果、页面反馈）；
4. 需要调整与保持不变的内容；
5. 关键正常/异常验收场景及待确认事项。

交互规格示例（示意，非企业实际流程）：

| 入口 | 操作 | 前置条件 | 页面反馈 | 状态/数据结果 |
|---|---|---|---|---|
| 审批待办详情 | 点击“提交审核意见” | 用户具备审核权限，意见完整 | 成功提示并返回待办 | 写入意见与处理记录 |
| 未开始阶段 | 点击“编辑” | 上游尚未完成 | 说明尚未开放原因 | 不改变数据 |

只要求“优化一个抽屉”时，仅给该抽屉的现状问题、改法和验收方式；不要输出整套 PRD。

## 6. 质量检查

- [ ] 页面服务的角色和主要任务清晰，核心任务有可见入口。
- [ ] 一级/二级导航、标签和步骤未表达重复层级。
- [ ] 组件选型符合信息量、频率、风险和上下文。
- [ ] 关键操作有前置条件、触发、状态结果和反馈。
- [ ] 只读、禁用、无权限和失败状态可识别且有解释。
- [ ] 保存、提交、审批、退回和发布未混为同一动作。
- [ ] 同类页面的术语、操作、字段和反馈一致。
- [ ] 跨角色任务有接收入口、处理出口和回流。
- [ ] 历史、版本、责任人信息满足当前任务需要。
- [ ] 变更范围最小，未修改未授权的业务规则。

## 7. 异常处理

- **业务规则缺失**：用待确认标记具体受影响交互，可继续设计确定部分。
- **截图与实际代码冲突**：先说明各自版本与差异，不把猜测当作现状。
- **重复导航或信息冲突**：指出重复层级及用户路径，优先消除冗余而不是追加一层。
- **组件无法支持完整流程**：说明交互代价，建议独立页面或分步操作，不强行塞入弹窗。
- **涉及越权或不可逆操作**：先明确角色、后果和确认机制，不擅自放开权限。
- **用户只要求交互方案**：不默认编写代码或推送仓库；用户明确授权时由实际执行环境完成。
